5. **Тарифы не зашивать в код.** Только из загруженных файлов (этап 2) и API Ozon.

7. Изменение структуры БД — SQL-патч в `sql/` + согласование с владельцем до наката.
8. Маленькие шаги: этап не больше ~15 файлов. Не переписывать то, что не требуется этапом.

## Решения владельца (не менять без согласования)

- Торгуем **с прибылью по цене, близкой к минимальной**. Минимальная = цена, которую реально платит покупатель
  после всех скидок (акция Ozon + наша акция), и при ней прибыль ≥ заданного минимума.
- **База прибыли:** положительная рыночная цена своей фасовки (`OZON_PERC.AVAILABLE_PRICE`, цена всей пачки)
  → иначе закупка за штуку × количество в фасовке → иначе «нет базы». Закупка: средневзвешенная по остатку
  партий → средневзвешенная по всем положительным приходам. Чужие фасовки и `MAX(AVAILABLE_PRICE)` не использовать.
  **Максимальный приход не использовать никогда.** Подставлять 1 ₽ нельзя.
- **Акции:**
  - товар в акции Ozon → цена после скидки Ozon **плюс** скидки нашей акции = минимальная; нашу скидку держать на минимуме;
  - товар только в нашей акции → цена после нашей скидки = минимальная;
  - товар не в акциях → пробуем добавить в акцию Ozon (правило 1), не берут — добавляем в нашу (правило 2).
    Наша акция нежелательна (скидки суммируются), но без неё не продать близко к минимальной.
- **Проверяем все товары кабинета**, а не только товары в акциях.
- **Схема FBO/FBS:** считаем по худшей (меньшая прибыль) из схем, где у товара есть остаток.
- **Ценовые ступени Ozon:** товаров до 100 ₽ нет. Число и границы ступеней берутся из загруженного файла.
  Для текущего файла рассчитываем два кандидата: по ставкам «100–300» и по ставкам «свыше 300».
  Проверяем принадлежность каждого своей ступени и выбираем меньшую допустимую цену.
- **Логистика:** FBS отгружаем из кластера **Новосибирск**. Направление доставки — **по реальным заказам**
  (взвешенное среднее). Сейчас в коде среднее min/max из API — это fallback, когда истории нет.
- **Кр (коэффициент снижения логистики за локальность) не учитываем** — считаем по предельному тарифу.
- **Возвраты:** процент **возвратов** (не отмен!) по артикулу, хранить в `OZON_PERC`, считать автоматически;
  без истории — 0 %.
- **Тарифы:** XLSX логистики и комиссий Ozon меняет еженедельно. Загружаются **через админку**;
  если файл старше 7 дней — **напоминание в бот Matrix (тема PRICES)**.

## Этап 1. Разбор убыточных заказов (только чтение, без кода в прод)

Цель — доказать, откуда убыток, на живых заказах, до правки формулы.

- Источник: журнал проверки прибыльности `MP_EVENT` kind `PROFIT_CHECK` (модуль `src/order/profit-check/`),
  тревоги «прибыли нет» за 30 дней, опт и магазин.
- На 5–10 заказах разложить: цена продажи (наша и покупательская), себестоимость (откуда взята),
  комиссия (схема, ступень), логистика, последняя миля, эквайринг, акции на момент заказа, налог.
  Сравнить с фактическим начислением Ozon (`/v3/finance/transaction/list` по posting).
- Результат: таблица «заказ → статья, на которой ушли в минус» + отчёт владельцу. Код не меняется.

## Этап 3. База прибыли (себестоимость) — ✅ Готово (исправление 8d4b190, 04.11.2026)

### Правило расчёта

1. `Trade2006GoodService.prices()` возвращает только закупочную цену **одной штуки**:
   средневзвешенная по остатку партий → средневзвешенная по количеству всех приходов → `null`.
   Приходы с нулевой/отрицательной ценой исключаются в обеих ветках. Рыночной цены в SQL больше нет.
2. `resolvePriceBase` в `src/helpers/price/price.base.ts` выбирает базу артикула:
   положительная AVAILABLE_PRICE только своей строки GOODSCODE + PIECES → иначе закупка × PIECES → `null`.
   AVAILABLE_PRICE уже хранится за пачку и повторно не умножается. Чужая фасовка не используется.
3. «Нет базы» определяется после проверки своей рыночной цены. Товар без приходов, но с собственной
   рыночной ценой, рассчитывается при наличии свободного остатка. Отсутствие свободного остатка сохраняет запрет.
   Явная подстановка входной цены не обходит отсутствие базы; ручная правка рыночной цены учитывается.
4. Общая функция используется через `getPriceBase`/`getIncomingPrice`, `collectPriceables`,
   `generatePercentsForService` и напрямую экраном `PriceService.index`. Проверка прибыльности заказов
   получает ту же базу через `buildPriceables`. Источники: market / remaining-lots / all-receipts / none.

## Этап 9. Экран цен (`admin-panel/src/components/Price.vue`, `stores/prices.ts`)

- Показывать результат функции этапа 6: цена, прибыль, разложение расходов, источник базы, ступень и схема.
- Правка процента → пересчёт тем же API, что использует отправка (никаких отдельных формул на фронте).
- Не смешивать на одной строке текущую цену Ozon и расчётную: две разные колонки.

Реализовано локально 05.11.2026; уточнения интерфейса согласованы владельцем. Backend: `fe97906`;
интерфейс и этот отчёт: коммит «Объединить расчёт цен и разделить сохранение с отправкой».

- Одна таблица содержит заданную и применённую наценку, текущие и расчётные цены Ozon,
  прибыль в рублях и процентах, схему и комиссию. Отдельный верхний блок показывает текущую
  цену покупателю и прибыль при ней. Оба результата считает формула этапа 6 на сервере.
- `GET /api/price/ozon-pricing/:offerId` принимает предварительные наценки, рекламу, упаковку
  и рыночную базу без сохранения. Ответ включает ограничения сервера, объяснение выбора
  ступени на границе 300 ₽ и источники расходов. Например, введённые 5% и применённые 10%
  показываются раздельно с указанием минимума сервера.
- Поля порога предупреждения сверху явно обозначены: они меняют подсветку, а не расчёт.
  Коэффициенты для расчёта берутся на сервере; устаревшие значения браузера не используются.
- Правка настройки запускает один отложенный расчёт. Текущие цены не подменяются расчётными.
  Предыдущий результат остаётся виден с индикатором обновления; запоздавшие ответы отбрасываются.
  При ошибке расчёта поля остаются доступны для исправления.
- «Загрузить текущие цены» обновляет данные площадки, сохраняя несохранённые настройки.
  «Пересчитать» обновляет предварительный расчёт. «Сохранить настройки» пишет только настройки
  товара, включая явно заданный ноль; цены на площадки эта кнопка не отправляет.
- «Отправить цены…» сначала запускает подготовку через `PreparePriceReviewCommand` и `JobService`.

  Расчёт использует существующие `buildPriceables` и `calculatePrice`, без копии формулы.
- После подтверждения `SendPriceReviewCommand` отправляет сохранённый на сервере снимок сумм.
  Предпросмотр действует 5 минут и хранится в памяти; повторное подтверждение возвращает ту же
  задачу. Подмена сумм в браузере не меняет отправку. Ошибки и ответы показаны отдельно по площадкам.
  Изменение настроек требует сохранения и новой подготовки. Старые API оставлены совместимыми.
