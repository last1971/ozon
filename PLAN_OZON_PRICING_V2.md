## Этап 0. Правила работы (обязательны для любого исполнителя)

1. **Только через git.** Каждый этап — отдельные коммиты в `main` (или ветка + PR). Сборку с незакоммиченного
   кода на прод **не выкатывать никогда**. Прод = то, что в git на сервере.
2. **Выкат — только по явному «го» владельца.** Пуш в `main` = автовыкат магазина (22.25). Опт (22.34) — руками
   (`git pull`, `npm install`, `npm run build`, `pm2 restart ozon --update-env`, `admin-panel: npm run build`).
   На 22.34 перед npm: `export NVM_DIR=$HOME/.nvm; . $NVM_DIR/nvm.sh`. Не больше одного рестарта прода в день.
3. **Перед пушем:** полный `npx jest` зелёный, `npm run build` и `admin-panel: npm run type-check` без ошибок.
4. **Одна функция расчёта.** Минимальную цену и прибыль считает одна функция (этап 6). Её зовут экран,
   отправка на Ozon, сверка акций и проверка прибыльности заказов. Копий формулы быть не должно.
5. **Тарифы не зашивать в код.** Только из загруженных файлов (этап 2) и API Ozon.
6. **Новые записи в Ozon — только после сухого прогона** (dryRun-отчёт владельцу) на опте.
7. Изменение структуры БД — SQL-патч в `sql/` + согласование с владельцем до наката.
8. Маленькие шаги: этап не больше ~15 файлов. Не переписывать то, что не требуется этапом.

## Решения владельца (не менять без согласования)

- Торгуем **с прибылью по цене, близкой к минимальной**. Минимальная = цена, которую реально платит покупатель
  после всех скидок (акция Ozon + наша акция), и при ней прибыль ≥ заданного минимума.
- **База прибыли:** рыночная цена (`OZON_PERC.AVAILABLE_PRICE`) → иначе средняя цена приходов → иначе товар
  не считать и показать «нет базы». **Максимальный приход не использовать никогда.** Подставлять 1 ₽ нельзя.
- **Акции:**
  - товар в акции Ozon → цена после скидки Ozon **плюс** скидки нашей акции = минимальная; нашу скидку держать на минимуме;
  - товар только в нашей акции → цена после нашей скидки = минимальная;
  - товар не в акциях → пробуем добавить в акцию Ozon (правило 1), не берут — добавляем в нашу (правило 2).
    Наша акция нежелательна (скидки суммируются), но без неё не продать близко к минимальной.
- **Проверяем все товары кабинета**, а не только товары в акциях.
- **Схема FBO/FBS:** считаем по худшей (меньшая прибыль) из схем, где у товара есть остаток.
- **Ценовые ступени Ozon:** товаров до 100 ₽ нет. Число и границы ступеней берутся из загруженного файла.
  Для текущего файла: сначала считаем по ставкам «100–300»; если цена ≤ 300 —
  берём её; иначе считаем по ставкам «свыше 300».
- **Логистика:** FBS отгружаем из кластера **Новосибирск**. Направление доставки — **по реальным заказам**
  (взвешенное среднее). Сейчас в коде среднее min/max из API — это fallback, когда истории нет.
- **Кр (коэффициент снижения логистики за локальность) не учитываем** — считаем по предельному тарифу.
- **Возвраты:** процент **возвратов** (не отмен!) по артикулу, хранить в `OZON_PERC`, считать автоматически;
  без истории — 0 %.
- **Тарифы:** XLSX логистики и комиссий Ozon меняет еженедельно. Загружаются **через админку**;
  если файл старше 7 дней — **напоминание в бот Matrix (тема PRICES)**.

## Этап 1. Разбор убыточных заказов (только чтение, без кода в прод)

Цель — доказать, откуда убыток, на живых заказах, до правки формулы.

- Источник: журнал проверки прибыльности `MP_EVENT` kind `PROFIT_CHECK` (модуль `src/order/profit-check/`),
  тревоги «прибыли нет» за 30 дней, опт и магазин.
- На 5–10 заказах разложить: цена продажи (наша и покупательская), себестоимость (откуда взята),
  комиссия (схема, ступень), логистика, последняя миля, эквайринг, акции на момент заказа, налог.
  Сравнить с фактическим начислением Ozon (`/v3/finance/transaction/list` по posting).
- Результат: таблица «заказ → статья, на которой ушли в минус» + отчёт владельцу. Код не меняется.

## Этап 6. Единый расчёт минимальной цены

Ценовые ступени читать из импортированных тарифов этапа 2. Порог 300 ₽ ниже — для текущего файла,
не постоянная граница в коде; при смене ступеней расчёт должен использовать новые диапазоны.

Одна чистая функция (без запросов наружу): вход — база, наценки, % рекламы, упаковка, этикетка, обработка, налог,
ставки комиссии по ступеням и схемам, логистика по ступеням и схемам, последняя миля, эквайринг, % возвратов,
мин. прибыль (₽) и мин. наценка (%), суммарная скидка акций. Выход — min/норм/макс цены, прибыль на каждой,
разложение расходов, источник базы.

- Ступени: считаем по «100–300»; результат ≤ 300 — берём; иначе по «свыше 300». Если на следующей ступени
  расходы ниже и цена «проваливается» под её границу — ставим границу + 1 ₽.
- **Мёртвая зона над 300 ₽ (находка этапа 1, 04.11.2026).** 4 из 10 убыточных заказов проданы за 312–326 ₽:
  цена перешла 300, комиссия прыгнула ~23 % → 47–51 %, логистика ~27 → ~142 ₽. Цена в диапазоне (300; P300],
  где P300 — минимальная цена по ставкам «свыше 300», убыточна. Правило: **любая** из цен min/норм/макс и цена
  после всех скидок акций либо ≤ 300, либо ≥ P300. Если норм./макс. по наценкам попадает в зону — поднять до P300.
  Если цена после скидок акций может попасть в зону — учитывать в этапе 7.
- Схема: считаем FBO и FBS (если есть остаток FBO), берём худшую.
- Прибыль ≥ max(мин. прибыль ₽, мин. наценка % × база).
- Заменить ею: `calculatePrice`/`calculatePay` для Ozon, `optimizeOzonPrice`, расчёт в profit-check.
- Проверка прибыльности заказов сейчас считает «мин» по ставкам текущей цены карточки, а не цены продажи:
  заказ 533987 за 228 ₽ (ставка 100–300, прибыль +17,81 ₽) дал ложную тревогу «мин 940». После замены функцией
  этапа 6 ставка и логистика берутся по цене продажи.
- Тесты: таблица примеров с ручным пересчётом (в т.ч. 560209-1: база 63,35, комиссия 51 %, логистика API).
